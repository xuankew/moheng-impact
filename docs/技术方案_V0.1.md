## 0. 结论摘要

V0.1 的核心链路是：

```text
Git Diff
  → Changed Symbols
  → Static Call Graph
  → Reverse Impact
  → Spring REST API
  → Risk
  → Report
```

技术定稿如下：

| 决策 | 结论 | 依据 |
|---|---|---|
| 分析引擎 | Spoon 11.5.0，源码级，不要求项目可构建 | 内部校准仓库 1,697 个类型解析 4.0–4.4s，1GB 堆可完成；无需内部 SNAPSHOT 依赖 |
| 技术栈 | 全 Java 单栈：Java 21 + Spring Boot 4.1 + React 19 | 引擎、JGit、服务端同栈；避免 Go/Java 双运行时与重复协议层 |
| 服务端 | Spring Boot + 静态 React Web | 单镜像、单容器、本地优先 |
| 存储 | SQLite（WAL）+ Flyway | 单用户本地场景足够；schema 可迁移到 PostgreSQL |
| 进程模型 | server/CLI 派生独立 analyzer-worker JVM | OOM/崩溃隔离；为 PRD §36 插件协议预留 |
| 分析范围 | 仅本地目录；Java + Spring MVC；head 单侧建模 | 已确认的 V0.1 收紧范围 |
| 图范围 | 只输出“影响子图”，不做全量图浏览器 | 避免产品退化为 Graph Viewer；控制 Web/DB 体积 |
| 项目 API 之外 | Git URL、PR、Compare、AI、覆盖率、Trace、测试选择全部延后 | 已确认的 V0.1 范围 |

校准仓库实测（只读，未修改、未提交）：

| 指标 | 实测值 |
|---|---:|
| 模型类型数（含内部类） | 1,697 |
| 源码解析耗时 | 3.97–4.42s |
| 端到端探针耗时 | 4.7–5.0s |
| 解析后已用堆（1GB 上限） | 274MB |
| Controller（按注解简单名） | 156 |
| 映射方法（含继承实例） | 679 |
| 其中继承自基类 Controller | 396 |
| 唯一 REST API（verb + path） | 689 |
| Feign 客户端 / 其映射方法 | 44 / 192 |
| Mapping 注解总数 | 831（795 字面量、35 数组字面量、1 无路径） |
| Lombok 类型 / `@Data` 类 / 字段 | 989 / 636 / 5,318 |
| AST 中已存在的 Lombok 访问器 | 0 |
| 项目内调用点 | 20,018 |
| 已解析项目内调用 | 5,302（26.5%） |
| 未解析但形似访问器 | 12,839 |
| 未解析的真实调用 | 1,877（9.4%） |
| 解析到接口的调用 | 1,899，涉及 220 个接口 |
| 有实现的接口 | 181（单实现 174、多实现 7） |

两个关键实测发现直接改变了实现方式：

1. **通配符 import 会让 noClasspath 模式下的 Spring 注解 FQN 落到当前包。** 例如 `import org.springframework.web.bind.annotation.*` 后，Spoon 把 `@RequestMapping` 解析成 `<当前包>.RequestMapping`。按 FQN 匹配只能识别 144 个 Controller；按“已知简单名 + 未解析包特征”可识别 156 个。V0.1 必须使用带守卫的简单名匹配，不能只用 FQN。
2. **Lombok 是调用图精度的主要缺口。** 989 个类型使用 Lombok，5,318 个 `@Data` 字段在 AST 中没有任何访问器方法；12,839 个项目内调用是形似 getter/setter 的未解析调用。补上 Lombok 虚拟访问器后，项目内调用理论覆盖率从 26.5% 提升到 90.6%；扣除少量非 Lombok 的访问器式调用，预计稳定在 88–90%，需在校准阶段验证。

## 1. 目标、边界与精度承诺

### 1.1 V0.1 目标

1. 用户 `docker compose up` 后 10 分钟内看到第一份真实影响报告。
2. 给定任意两个 Git 版本（或 base 与工作区），输出：
   - 变更文件、变更符号；
   - 受影响方法；
   - 受影响 REST API；
   - 从变更符号到 API 的影响路径；
   - 风险等级、风险原因、Safe Mode 提示。
3. CLI 在 CI 中可直接使用，输出稳定 JSON，并支持风险阈值失败。
4. 全流程离线、无遥测、不上传源码。
5. Apache-2.0 发行，依赖许可合规。

### 1.2 V0.1 明确不做

```text
Git URL / GitHub / GitLab / PR 接入
Compare Analysis
AI / LLM 能力
JaCoCo / 覆盖率
OpenTelemetry / Trace / Runtime Agent
精准 Test Selection
多语言
跨仓库分析
图数据库
用户自定义风险规则（只保留配置文件预留）
PostgreSQL 服务端部署
登录 / 多租户 / 权限
```

### 1.3 精度承诺（可验证，不夸大）

V0.1 承诺的是“可解释的静态影响”，不是“运行时真实调用全集”：

| 能力 | 承诺 |
|---|---|
| 变更符号 | 方法/字段级识别；注释与纯格式变化不产生变更符号 |
| Controller 识别 | `@RestController` / `@Controller`；含继承映射；校准仓库 156/156 |
| API 识别 | 类级 + 方法级路径组合；数组路径；继承 Mapping；Feign 不算本地 API |
| 项目内调用解析 | 校准仓库非 Lombok 部分 73.8%；补 Lombok 后目标 ≥88%；未解析部分显式计入边界 |
| 接口分派 | 单实现接口展开；多实现按规则展开并降置信度 |
| 重写方法 | `OVERRIDES` 双向传播 |
| 影响路径 | 默认最大深度 5；每条边有置信度；路径置信度取最小值 |
| 风险 | 规则化、可解释；Safe Mode 覆盖构建/配置/schema/公共模块/鉴权/序列化/公共 DTO |
| 动态能力 | 不承诺；反射、AOP 代理、SpEL、消息、定时任务、Feign 远端调用按边界处理 |

### 1.4 与 PRD V0.2 的偏差

| PRD 方案 | V0.1 方案 | 原因 |
|---|---|---|
| Server/CLI/Core 用 Go | 全 Java 21 | 引擎与 JGit 均为 JVM；单栈单镜像；实测分析 1,697 类型 <5s，Go 的性能优势不构成收益；避免双运行时和重复协议实现 |
| SCIP + SootUp | Spoon 源码级 | SCIP/SootUp 都依赖成功构建；校准仓库含大量内部 SNAPSHOT 依赖，外部环境不可构建。Spoon 已实测可直接解析 |
| PostgreSQL | SQLite | 本地单用户、单容器；schema 与查询保持可迁移；V0.2 服务端版再引入 PostgreSQL |
| Node 类型含 CLASS/METHOD/API | 增加 FIELD，并增加 `READS/WRITES` 类引用边 | 字段变更与 Lombok 访问器是 Java 影响分析的必要组成；PRD §19 已把 field 纳入 Changed Symbol |
| Confidence 仅 4 档 | 扩展为 8 档 | 区分继承映射、Lombok、单/多实现、重写分派与启发式解析 |
| 每次分析保存全图 | 只保存影响子图 + API/变更摘要 | 控制 DB 与 Web 规模；全量图对 V0.1 用户无直接价值 |

## 2. 总体架构

```text
┌──────────────────────────── Browser ────────────────────────────┐
│ React 19 + TypeScript + Vite + Tailwind + shadcn/ui             │
│ React Flow + dagre + TanStack Query                             │
└───────────────────────────────┬─────────────────────────────────┘
                                │ HTTP /api
┌───────────────────────────────▼─────────────────────────────────┐
│ Spring Boot 4.1 (Java 21)                                       │
│  ├── REST API + 静态 Web                                        │
│  ├── AnalysisService（排队、状态、取消、超时）                    │
│  ├── SQLite（WAL）/data/moheng.db + Flyway                      │
│  └── 派生 worker 子进程（-Xmx1g，可配置）                         │
└───────────────────────────────┬─────────────────────────────────┘
                                │ JSON 请求文件 + JSONL 进度 + JSON 结果
┌───────────────────────────────▼─────────────────────────────────┐
│ analyzer-worker（独立 JVM）                                      │
│  ├── JGit：diff / blob 读取 / worktree 变更                       │
│  ├── Spoon：head 源码模型                                        │
│  ├── ChangeDetector：变更符号                                     │
│  ├── GraphBuilder：调用/字段/实现/重写/API 绑定                    │
│  ├── ImpactEngine：反向遍历、路径、置信度                          │
│  └── RiskEngine：API 风险、Safe Mode                             │
└───────────────────────────────┬─────────────────────────────────┘
                                │
                     /workspace/<repo>（只读）
```

CLI 复用同一 worker：

```text
mh impact analyze → 派生 worker → report.json / text
mh impact serve   → 启动内嵌 Spring Boot（与 Docker 同入口）
```

### 2.1 进程隔离

- 每次分析启动一个 worker JVM；默认并发 1，队列上限 4。
- worker 参数：`-Xmx${MOHENG_WORKER_HEAP:-1g}`、`-XX:+ExitOnOutOfMemoryError`、`-Dfile.encoding=UTF-8`。
- 默认超时 10 分钟；超时先 `destroy()`，3 秒后 `destroyForcibly()`。
- worker 崩溃/OOM 只影响当前 run，server 标记 `FAILED` 并返回明确错误码。
- 进度通过 stdout JSONL 上报，server 逐行解析并更新内存状态；Web 轮询 1s。

### 2.2 为什么不是“一次请求内同步分析”

- 1,697 类型约 5s，但真实仓库可能 10k+ 类型；HTTP 长连接不可靠。
- 需要取消、超时、历史记录与进度。
- worker 崩溃不能拖垮 Web。

### 3.1 为什么是 Spoon，不是 SCIP / SootUp / JavaParser

| 方案 | 是否要求可构建 | 类型/声明解析 | 结论 |
|---|---|---|---|
| SCIP | 是，依赖构建产物与索引器 | 高 | 校准仓库内部 SNAPSHOT 依赖不可获取，无法作为 V0.1 默认引擎；P1 可作为高精度模式 |
| SootUp | 是，依赖字节码 | 高 | 同上 |
| JavaParser | 否 | 需自建 Symbol Solver 与方法解析/继承/注解逻辑 | 能做，但等于重写 Spoon 已提供的能力；无收益 |
| Spoon | 否 | 源码模型 + 声明解析 + 继承/注解遍历 | 实测通过，定稿 |

Spoon 的代价是“无完整类型归因”。V0.1 用四条规则兜底：精确解析、接口/实现展开、Lombok 虚拟访问器、名称+参数个数启发式；无法解析的调用明确计入边界，不伪造边。

### 3.2 为什么全 Java，而不是 Go server/CLI

- 引擎只能跑在 JVM；Go 方案仍要维护 Java analyzer 与 JSON 协议，等于双栈。
- 分析是 CPU/内存型短任务，实测 5s；server 是轻量 CRUD，不存在 Go 的性能必要。
- JGit、Jackson、Picocli、Spring Boot 在同一生态，模型定义只维护一份。
- 单镜像、单构建链、单套排障方式，符合“本地优先、10 分钟用起来”。
- 代价：JVM 启动与常驻内存。通过 worker 隔离、CDS、可选 native-image CLI 缓解；V0.1 不做 native-image。

### 3.3 许可合规

- Spoon 采用 MIT 选项，发行物中附 MIT 许可证与版权声明。
- JGit 为 EDL-1.0 / EPL-2.0 双许可，未修改依赖，附 NOTICE 与许可证。
- SQLite JDBC、Flyway、Spring Boot、Picocli、React 等均为 Apache-2.0/MIT。
- 产品代码 Apache-2.0；`NOTICE` 聚合第三方声明；Docker 镜像内保留 licenses 目录。
- 不使用任何内部仓库源码、路径或数据作为测试夹具或 Demo。

## 5. 数据模型

### 5.1 Node

V0.1 使用：

```text
FILE
CLASS
METHOD
FIELD
API
```

节点 key 规范：

```text
FILE:   FILE:<repo-relative-path>
CLASS:  CLASS:<fqn>
METHOD: METHOD:<fqn>#<name>(<param-type-1>,<param-type-2>):<return-type>
FIELD:  FIELD:<fqn>#<field-name>
API:    API:<VERB> <normalized-path>
```

方法签名使用 Spoon 的 source signature；构造器为 `<init>`。参数类型保留源码类型名，不擦除泛型；重载因此可区分。

### 5.2 Edge

```text
DEFINES        CLASS/FILE → METHOD/FIELD
CALLS          METHOD → METHOD
REFERENCES     METHOD → FIELD（detail: FIELD_READ / FIELD_WRITE）
IMPLEMENTS     CLASS → CLASS/INTERFACE
EXTENDS        CLASS → CLASS
OVERRIDES      METHOD → METHOD
EXPOSES_API    METHOD → API
```

边字段：

```json
{
  "from": "METHOD:com.acme.OrderService#submit(OrderForm):Result",
  "to": "METHOD:com.acme.CouponService#use(String):void",
  "type": "CALLS",
  "confidence": 1.0,
  "detail": "DIRECT",
  "evidence": {
    "source": "STATIC",
    "file": "src/main/java/com/acme/OrderService.java",
    "line": 88,
    "receiverType": "com.acme.CouponService",
    "annotationResolution": "FQN"
  }
}
```

不存源码片段。UI 需要上下文时通过受控接口按行读取仓库内容，避免源码进入 DB/日志。

### 5.3 API

`apiId` 为 `sha256(key)` 前 16 位十六进制，用于 URL；`key` 保留完整可读标识。

```json
{
  "id": "a1b2c3d4e5f6a7b8",
  "key": "API:POST /internal/shop/page",
  "verb": "POST",
  "path": "/internal/shop/page",
  "controller": "com.acme.shop.InternalShopController",
  "handler": "com.acme.shop.CommonShopController#page(ShopPageForm):Result",
  "mapping": {
    "classPath": ["internal/shop"],
    "methodPath": ["page"],
    "conditions": {"consumes": [], "produces": [], "params": [], "headers": []},
    "annotationResolution": "SIMPLE_NAME_FALLBACK",
    "inherited": true
  },
  "confidence": 1.0
}
```

路径规范化：

1. `apiPrefix`（项目配置）→ 类级路径 → 方法级路径；
2. 合并连续 `/`；
3. 保证以 `/` 开头；
4. 去掉末尾 `/`（根路径除外）；
5. 保留 `{var}` 与正则片段，大小写敏感；
6. `@RequestMapping` 未声明 method → `ANY /path`，不展开成 7 个动词。

同一 `VERB + path` 若由多个 Controller 暴露，key 追加 `@<controller-fqn>` 并产生 `AMBIGUOUS_API_PATH` 警告。

### 5.4 ImpactPath

```json
{
  "changed": "METHOD:com.acme.CouponService#use(String):void",
  "api": "API:POST /api/order",
  "depth": 3,
  "confidence": 0.9,
  "edges": ["...edgeId...", "..."]
}
```

路径置信度 = 路径上所有边置信度的最小值。API 置信度 = 所有到达该 API 的路径置信度的最大值。

### 5.5 Confidence

| 场景 | 值 | 说明 |
|---|---:|---|
| 精确解析的直接调用 | 1.0 | Spoon 解析到声明 |
| 继承 Mapping（API 绑定） | 1.0 | 结构性事实 |
| 字段读写（精确解析） | 1.0 | 字段声明存在 |
| Lombok 确定性访问器 | 0.95 | 注解 + 字段 + 无显式同名方法 |
| 单实现接口展开 | 0.9 | 项目内唯一实现 |
| 多实现接口展开（每个候选） | 0.85 | 存在分派不确定性 |
| 重写方法分派 | 0.85 | 基类声明被调用，子类重写 |
| Mapping 路径常量/拼接 | 0.8 | 表达式可提取但非字面量 |
| 名称 + 参数个数启发式 | 0.6 | 接收者类型在项目内，声明未解析 |
| 未解析调用 | 无边 | 计入边界统计，不伪造 |

UI 提供“仅高置信度”过滤，阈值 0.8；默认展示全部并标注低置信度边。

### 5.6 图规模控制

- worker 只输出“影响子图”：变更节点、被影响节点、Controller 方法、API 节点及其路径上的边。
- 默认上限：节点 2,000、边 5,000；超出时保留最高置信度/最短路径并返回 `GRAPH_TRUNCATED` 警告。
- 全图只保留统计计数，不落库、不回传。

## 6. 分析流水线

### 6.1 阶段与进度

| 阶段 | 进度 | 输出 |
|---|---:|---|
| PREFLIGHT | 0–5% | 仓库校验、revision 解析、参数校验 |
| DIFF | 5–15% | 变更文件、行区间、增删改/重命名 |
| PARSE | 15–45% | head Spoon 模型、解析错误计数 |
| SYMBOLS | 45–55% | 变更符号、变更类型、API 契约变更 |
| GRAPH | 55–75% | 方法/字段/调用/实现/重写/API 绑定 |
| IMPACT | 75–88% | 受影响方法、API、影响路径 |
| RISK | 88–95% | API 风险、报告风险、Safe Mode |
| PERSIST | 95–100% | 结果序列化与回传；server 落库并收尾 |

进度通过 JSONL 输出：

```json
{"type":"progress","phase":"PARSE","percent":30,"message":"parsed 900/1697 types"}
```

### 6.2 Preflight

- `repoPath` 必须位于配置的 workspace root 下；canonical path 校验，拒绝 `..` 与 symlink 逃逸。
- 必须是 Git 工作区（非 bare）；允许 shallow，但 base 不可达时明确失败。
- `base`/`head` 通过 JGit `resolve(rev + "^{commit}")` 解析；失败返回 `REVISION_NOT_FOUND`。
- 限制：Java 文件数默认 20,000、源码总大小 200MB、diff 文件数 10,000；超限明确报错，不静默截断。
- 过滤：`src/test/java`、`target/`、`build/`、`.git/`、`generated/` 默认排除；支持 include/exclude 包。

### 6.3 Git Diff

- `head=<rev>`：`DiffFormatter` 双树 diff，开启重命名检测（阈值 60%）。
- `head=WORKTREE`：JGit `IndexDiff` 获取 modified/added/untracked/deleted；遵守 `.gitignore`。
- 输出每个文件的 `ADDED / MODIFIED / DELETED / RENAMED`、旧路径、hunk 行区间、二进制标记。
- 非 Java 文件只用于 Safe Mode 与报告，不进入符号分析。
- 行区间只用于 UI 展示；变更符号以符号身份比对为准，避免行号漂移导致误报。

### 6.4 head 模型解析

- 扫描仓库内所有 `*/src/main/java` 作为源码根；支持项目配置追加 `sourceRoots`。
- `head=WORKTREE`：直接读取文件系统。
- `head=<rev>`：通过 JGit `ObjectLoader` 读取 blob，用 Spoon `VirtualFile` 构建模型，不要求 checkout。
- Spoon 配置：

```java
setNoClasspath(true);
setComplianceLevel(project.javaVersion); // 默认 21；Java 8 源码已实测可解析
setIgnoreSyntaxErrors(true);             // 继续分析，但结果中报告解析错误
setCommentEnabled(false);
setLevel("ERROR");
```

- 记录解析失败文件数与文件名（不记录源码内容），返回 `PARSE_ERRORS` 警告；超过阈值（默认 5%）时降低整体置信度提示。
- 不执行 Maven/Gradle，不下载依赖，不写仓库。

### 6.5 变更符号

符号身份：

```text
METHOD: <fqn>#<name>(<param-types>):<return-type>
FIELD:  <fqn>#<field-name>
CLASS:  <fqn>
```

比对流程：

1. 对每个变更 Java 文件，从 base revision 读取 blob，在独立的 base Spoon 模型中解析。
2. head 模型定位同一文件（重命名用 JGit 映射）的所有类型与成员。
3. 按身份匹配；base 有 head 无 → REMOVED；head 有 base 无 → ADDED；同身份 → 比较指纹。
4. 方法指纹 = 参数类型 + 参数名 + 参数注解 + 返回类型 + 异常 + 方法注解 + 规范化方法体。
5. 字段指纹 = 类型 + 修饰符 + 注解 + 初始化表达式。
6. 类指纹 = 修饰符 + 注解 + 父类 + 接口。
7. 注释、空行、纯格式变化被忽略（注释关闭，方法体规范化）。

变更类型：

| 类型 | 判定 | 影响 |
|---|---|---|
| `METHOD_BODY_MODIFIED` | 指纹变化但签名不变 | 反向影响调用者 |
| `METHOD_SIGNATURE_CHANGED` | 身份变化 | 旧方法 REMOVED + 新方法 ADDED；风险提升 |
| `METHOD_ANNOTATION_CHANGED` | 方法注解变化 | Controller 映射变化视为 API 契约变更 |
| `FIELD_MODIFIED` | 字段类型/名称/注解/初始化变化 | 反向影响读写者；公共 DTO 触发 Safe Mode |
| `CLASS_MODIFIED` | 类注解/继承关系变化 | 类内方法与字段按结构变化传播 |
| `FILE_ADDED / FILE_DELETED` | 文件级增删 | 全部符号增删 |

补充规则：

- 局部变量重命名会导致方法体指纹变化，V0.1 接受这一少量误报，并在文档中注明。
- 参数名变化不改变 Java 签名，但可能改变 Spring 绑定；标记为 `CONTRACT_CHANGED`，不拆成删+增。
- Controller 的 Mapping 注解变化会进入 API 契约 diff。

### 6.6 API 契约变更

- 从 base revision 解析全部 Controller 文件及其父类/接口（约 156 个文件），构建 base API 清单。
- 与 head API 清单做 key diff：
  - `API_REMOVED`：契约破坏，风险 +30；
  - `API_ADDED`：风险 +5；
  - 同 key 但 handler/conditions 变化：`API_CHANGED`，风险 +30。
- 该 diff 能覆盖“改基类 Mapping 影响多个子类”的情况，因为 base 侧解析了全部 Controller 及其继承链。
- 报告中单列“API 契约变更”，不混在影响路径里。

### 6.7 图构建

构建顺序：

1. 为项目内所有类型建立 CLASS 节点；为方法/构造器建立 METHOD 节点；为字段建立 FIELD 节点。
2. 遍历所有方法体中的 `CtInvocation`：
   - 精确解析到项目内声明 → `CALLS`，confidence 1.0；
   - 解析到接口方法 → `CALLS` 到接口方法 + 展开实现（见 7.2）；
   - 解析到基类方法但存在子类重写 → 额外 `OVERRIDES`/分派边（见 7.3）；
   - 未解析但接收者类型在项目内 → 名称+参数个数启发式，confidence 0.6；候选超过 3 个则放弃并计入边界；
   - 未解析且接收者在项目外 → 边界，不建边。
3. 字段访问：
   - `CtFieldRead` → `REFERENCES(FIELD_READ)`；
   - `CtFieldWrite` / 赋值左侧 → `REFERENCES(FIELD_WRITE)`；
   - Lombok 访问器调用 → 解析为对应字段读写，confidence 0.95。
4. 继承关系：`EXTENDS`、`IMPLEMENTS`。
5. Controller 绑定：
   - 对每个 head Controller，使用 `getAllMethods()` 取出映射方法（含继承）；
   - 组合类级/方法级路径与动词，生成 API 节点；
   - 建 `EXPOSES_API`：handler 方法 → API；
   - 继承映射的 API 归属子类 Controller，同时记录 handler 的声明类型。
6. Feign：
   - 任何带 `@FeignClient` 的类型不进入本地 Controller/API 清单；
   - 其映射方法计数单列为 `externalClients`，不建本地 API；
   - 本地代码调用 Feign 接口视为外部边界。

### 6.8 反向影响

- 起点：变更方法、变更字段、变更类（类级变化展开为类内方法/字段与构造器）。
- 图方向：`CALLS`/`REFERENCES` 为“调用者 → 被调用者/字段”；反向 BFS 从被变更者走向调用者。
- `EXPOSES_API` 为“handler → API”；反向 BFS 到达 handler 后产出 API 影响。
- 默认 `maxDepth=5`（PRD §22）；可配置 1–10。
- 每个节点记录“最佳置信度”和“最短深度”；同一节点不重复展开。
- 环检测用 visited；环不导致无限遍历。
- 每个（变更符号, API）保留一条代表路径：优先置信度高、其次深度短；API 最多保留 10 条路径，超出计数。
- 输出受影响方法集合、受影响 API 集合、路径、边界统计。

### 7.2 注解匹配规则（关键）

Spoon noClasspath 下，通配符 import 会导致注解 FQN 误解析。匹配器按以下顺序：

1. FQN 精确命中已知 Spring 注解；
2. 简单名命中，且满足任一“未解析特征”：
   - 注解 FQN 不含包名；或
   - 注解 FQN 的包等于当前类型的包（通配符 import 的误解析结果）；
3. 守卫：若项目自身定义了同名注解类型，则只接受 FQN 精确匹配，避免把自定义注解误判为 Spring。

命中简单名回退时，在 evidence 记录 `annotationResolution: SIMPLE_NAME_FALLBACK`。实测该校准仓库从 144 个 Controller 修正为 156 个。

### 7.3 继承、接口与重写

- Controller 继承：`getAllMethods()` 遍历，映射方法按子类类级前缀组合；同一基类方法可被多个子类暴露为不同 API。
- 接口分派：
  - 单实现（校准仓库 174/181）：展开到唯一实现，confidence 0.9；
  - 多实现：最多展开 5 个实现，confidence 0.85；超过 5 个（如 `BaseRepository` 34 个实现）不展开，记录 `HIGH_FANOUT_INTERFACE`，避免噪声爆炸。
- 重写：
  - 建 `OVERRIDES` 边；
  - 调用解析到基类方法时，若存在子类重写，增加分派边，confidence 0.85；
  - 反向影响从重写方法可到达基类调用者，从基类变更可到达重写实现。
- 构造器与字段注入：`@Resource/@Autowired` 字段不需要额外 Bean 装配；Spoon 通过字段静态类型解析调用。

### 7.4 Lombok

实测：989 个 Lombok 类型、636 个 `@Data` 类、5,318 个字段、AST 中 0 个访问器。

V0.1 不生成虚拟方法节点，而是把访问器调用解析为字段读写边：

| 场景 | 规则 | 置信度 |
|---|---|---:|
| `@Data` / `@Getter` / `@Setter` 字段 | 按 JavaBeans 命名生成 get/set | 0.95 |
| 基本类型 boolean | `isX()` | 0.95 |
| 字段首字母缩写（如 `URL`） | 按 `Introspector.decapitalize` 逆规则 | 0.95 |
| 显式同名方法存在 | 以显式方法为准，不生成虚拟访问器 | 1.0 |
| `@Accessors(fluent=true)` | 方法名 = 字段名 | 0.9 |
| `@Builder` 链式调用 | 解析 `Type.builder()` 为类引用；链式 setter 未解析 | 0.8 / 边界 |
| static 字段 | 不生成实例访问器 | — |

`@Builder` 在校准仓库仅 3 个类型，V0.1 接受降级；报告中单列未解析构建器调用计数。

### 7.5 未解析调用的处理

校准仓库 1,877 个“真实未解析调用”，主要来自：

- MyBatis-Plus `IService#info`、`lambdaQuery`、`BaseMapper#selectById/updateById`；
- 外部 SNAPSHOT 基类方法；
- Lambda/方法引用；
- 事务模板 `execute`。

处理原则：

- 这些调用指向框架/外部代码，不产生用户代码影响边；
- 计入 `externalBoundaryCalls`，在报告中展示总数与前缀分布（不展示源码）；
- 不因未解析而把“所有 API”标为受影响；
- 若变更符号本身位于这些外部基类的子类中，仍通过类内调用与 API 暴露分析；
- 解析错误率超过阈值时，报告整体置信度提示。

## 8. 风险引擎与 Safe Mode

### 8.1 API 风险

每个受影响 API 独立评分（0–100）：

| 规则 | 权重 | 说明 |
|---|---:|---|
| 直接修改 Controller handler | +30 | API 行为直接变化 |
| 影响路径深度 1–2 | +10 | 近距离 |
| 影响路径深度 3–4 | +20 | 中距离 |
| 影响路径深度 ≥5 | +25 | 远距离、放大风险 |
| API 置信度 < 0.8 | +5 | 不确定性 |
| 变更符号 fan-in ≥10 | +10 | 共享组件 |
| 变更符号签名变化 | +15 | 兼容性风险 |
| 公共 DTO 字段变化 | +20 | 请求/响应契约 |
| API 契约删除/变更 | +30 | 直接破坏调用方 |
| 核心 API 关键字（order/pay/auth/coupon 等，可配置） | +10 | 业务关键路径 |

等级：

```text
0–19   LOW
20–39  MEDIUM
40–59  HIGH
60–100 CRITICAL
```

API 页面展示每条命中的规则、权重与证据。

### 8.2 报告风险

```text
reportScore = max(所有 API 分数)
若 Safe Mode：reportScore = max(reportScore, 60)，等级至少 HIGH
若 Safe Mode 且（触发项 ≥3 或受影响 API ≥20）：reportScore = max(reportScore, 80)，等级 CRITICAL
```

Safe Mode 是报告级标志，不把每个 API 都强行标成 HIGH；UI 顶部展示全局横幅，API 列表保留各自分数。

| 公共 DTO | 包名含 `dto/vo/form/request/response`，或类名后缀 DTO/VO/Form/Request/Response，且变更 public 字段/类 | 触发 |
| 框架配置 | `@Configuration`、`WebMvcConfig`、`spring.factories`、`META-INF/spring/**` | 触发 |
| CI/部署 | `Dockerfile`、`docker-compose*.yml`、`.gitlab-ci.yml`、`.github/workflows/**` | 触发（较低权重） |

## 9. Server 设计

### 9.1 运行形态

- Spring Boot 4.1，Java 21，内嵌 Tomcat。
- 静态 Web 由 server 提供；`/api/**` 为 REST。
- 默认绑定 `127.0.0.1`；Docker 中仍绑定容器内 `0.0.0.0` 但只发布到宿主机 `127.0.0.1:8848`。
- 无登录、无多租户；本地单用户。
- 单实例；分析并发 1。

**存储选型说明**：V0.1 选 SQLite，不是因为它“更简单所以将就”，而是因为它与“单容器、本地优先、单用户”的部署模型完全匹配：零额外进程、零账号/端口/初始化、一个文件即数据库、备份就是复制文件；分析写入集中在每次 run 结束时的一个事务，且并发为 1，SQLite 的单写者限制不构成问题，WAL 足以支撑 Web 轮询读。PostgreSQL/MySQL 都是客户端-服务端数据库，会额外引入一个容器、启动等待、凭据、网络与健康检查，直接破坏“`docker compose up` 后 10 分钟看到报告”的目标。MySQL 相比 SQLite 没有解决 V0.1 的任何实际问题；若未来进入集中部署/多用户/多实例，升级目标是 PostgreSQL 而不是 MySQL：结果 JSON 可用 JSONB + GIN 索引，许可证为宽松的 PostgreSQL License，避免 Oracle MySQL 的 GPL/商业双许可审查。当前 schema 不使用 SQLite 特有类型，JSON 以 TEXT 存储，迁移成本可控。SQLite 文件不要放在 NFS 等网络文件系统上。

| GET | `/api/analyses/{id}/status` | 状态与进度（轮询） |
| GET | `/api/analyses/{id}/apis?risk=&q=&page=` | API 列表（分页/过滤） |
| GET | `/api/analyses/{id}/apis/{apiId}` | 单个 API 详情与路径 |
| GET | `/api/analyses/{id}/changes` | 变更文件与符号 |
| GET | `/api/analyses/{id}/graph?apiKey=&changed=&maxDepth=` | 影响子图（可过滤） |
| GET | `/api/analyses/{id}/source?file=&start=&end=` | 受控源码片段（只读） |

响应统一：

{"data": {}}

### 9.3 分析生命周期

```text
QUEUED → RUNNING → SUCCEEDED | FAILED | CANCELLED
```

- `POST /analyses` 返回 `202` + runId；后台线程排队并派生 worker。
- Web 每 1s 轮询 `/status`；阶段/百分比来自 worker JSONL。
- 取消：设置标志 + 销毁进程；状态置 `CANCELLED`。
- server 重启：将 `RUNNING/QUEUED` 标记为 `FAILED`，错误码 `SERVER_RESTARTED`；不做断点续跑。

### 9.4 Worker 协议

请求文件：

```json
{
  "protocolVersion": "1",
  "runId": "...",
  "repoPath": "/workspace/repo",
  "base": "main",
  "head": "WORKTREE",
  "options": {
    "headMode": "AUTO",
    "maxDepth": 5,
    "apiPrefix": "",
    "javaVersion": 21,
    "includePackages": [],
    "excludePackages": [],
    "sourceRoots": [],
    "includeTests": false,
    "highConfidenceOnly": false
  }
}
```

- `headMode`：`AUTO` → 若 head 解析为 `WORKTREE` 则工作区，否则按 commit blob；也允许显式 `REV_COMMIT / WORKTREE`。
- 结果文件：完整 `Result` JSON（见 6.10）。
- stdout：仅 JSONL 进度；stderr：错误摘要（不含源码）。
- worker 退出码：0 成功；2 参数错误；3 分析错误；4 解析失败超阈值。OOM 由 `ExitOnOutOfMemoryError` 终止进程，server 依据退出码与错误输出标记 `WORKER_OOM`。
- 请求/结果文件放在 `/data/tmp/<runId>/`，完成后删除。

### 9.5 SQLite schema

```sql
CREATE TABLE project (
  id              TEXT PRIMARY KEY,
  name            TEXT NOT NULL,
  repo_path       TEXT NOT NULL UNIQUE,
  api_prefix      TEXT NOT NULL DEFAULT '',
  include_packages TEXT NOT NULL DEFAULT '[]',
  exclude_packages TEXT NOT NULL DEFAULT '[]',
  source_roots    TEXT NOT NULL DEFAULT '[]',
  default_base    TEXT,
  created_at      TEXT NOT NULL,
  updated_at      TEXT NOT NULL
);

CREATE TABLE analysis_run (
  id            TEXT PRIMARY KEY,
  project_id    TEXT NOT NULL REFERENCES project(id) ON DELETE CASCADE,
  base_rev      TEXT NOT NULL,
  head_rev      TEXT NOT NULL,
  head_mode     TEXT NOT NULL,
  status        TEXT NOT NULL,
  phase         TEXT,
  progress      INTEGER NOT NULL DEFAULT 0,
  risk_level    TEXT,
  risk_score    INTEGER,
  safe_mode     INTEGER NOT NULL DEFAULT 0,
  summary_json  TEXT,
  result_json   TEXT,
  error_code    TEXT,
  error_message TEXT,
  warnings_json TEXT,
  started_at    TEXT NOT NULL,
  finished_at   TEXT
);

CREATE TABLE api_impact (
  run_id       TEXT NOT NULL REFERENCES analysis_run(id) ON DELETE CASCADE,
  api_id       TEXT NOT NULL,
  api_key      TEXT NOT NULL,
  verb         TEXT NOT NULL,
  path         TEXT NOT NULL,
  controller   TEXT NOT NULL,
  handler      TEXT NOT NULL,
  risk_level   TEXT NOT NULL,
  risk_score   INTEGER NOT NULL,
  confidence   REAL NOT NULL,
  depth        INTEGER NOT NULL,
  reasons_json TEXT NOT NULL,
  PRIMARY KEY (run_id, api_id)
);

CREATE TABLE change (
  run_id      TEXT NOT NULL REFERENCES analysis_run(id) ON DELETE CASCADE,
  file_path   TEXT NOT NULL,
  change_type TEXT NOT NULL,
  symbol_key  TEXT,
  symbol_kind TEXT,
  detail_json TEXT
);

CREATE INDEX idx_run_project_started ON analysis_run(project_id, started_at DESC);
CREATE INDEX idx_api_impact_run_risk ON api_impact(run_id, risk_score DESC);
CREATE INDEX idx_change_run_file ON change(run_id, file_path);
```

- Flyway `V1__init.sql`；SQLite 开启 `WAL`、`busy_timeout=5000`、`foreign_keys=ON`、`synchronous=NORMAL`。
- `result_json` 为完整报告；列表/筛选读 `api_impact`；历史对比后续复用 `change`/`api_impact`。
- 单写者（server）；worker 不直接写 DB。

### 9.6 源码片段接口

- `GET /source` 仅允许 `file` 位于该项目 repoPath 下，canonical 校验。
- 读取 head 侧内容：`WORKTREE` 读文件系统；commit 读 JGit blob。
- 最多返回 200 行；响应为纯文本；不缓存完整文件。
- 该接口用于 UI 证据上下文，不进入日志。

### 9.7 安全边界

- 无遥测、无外部网络请求。
- 路径逃逸防护：workspace root、项目 repoPath、source 文件三层 canonical 校验。
- 仓库建议只读挂载；应用自身绝不写仓库。
- 日志只记录计数、耗时、路径、错误码；不记录源码、Token、Git 凭据。
- Git URL 接入未实现，V0.1 不存储任何凭据。
- Docker 以非 root 用户运行；`/data` 可写，其余只读（可选 read-only rootfs + tmpfs `/tmp`）。

1. 选取变更集：小（1–5 文件）、中（10–50 文件）、大（发布分支 diff）。

   - 变更符号 recall/precision；
   - API recall/precision；

   - 继承映射覆盖；
   - Feign 误报数（必须为 0）；

4. 目标：
   - 变更符号 recall ≥95%（方法/字段级）；
   - 受影响 API recall ≥85%；
   - API 误报率 ≤15%；
   - 高置信度路径 precision ≥95%；

   - 1,697 类型仓库 <30s、峰值 RSS <1.5GB、0 崩溃。

## 15. 风险与缓解

| 风险 | 影响 | 缓解 |
|---|---|---|
| 通配符 import 导致注解误判 | Controller/API 漏识别 | 简单名回退 + 自定义注解守卫；已实测 144→156 |
| Lombok 访问器缺失 | 调用图断裂、影响漏报 | 字段读写虚拟边 0.95；校准解析率 ≥95% |
| 继承 Controller 映射漏识别 | API 漏报 | `getAllMethods()`；实测 396 继承实例；夹具覆盖 |
| Feign 被误当本地 API | API 误报 | 显式排除；44 客户端/192 方法；e2e 断言 |
| 运行时前缀未知（Nacos/网关） | 路径与真实调用不一致 | `apiPrefix` 配置；不猜测；README 明确 |
| 动态代理/AOP/反射/SpEL | 影响漏报 | 边界统计 + 风险提示；V0.2 引入运行时证据 |
| 多实现接口展开噪声 | API 误报 | 最多 5 个实现；超过则告警不展开 |
| 大仓库内存/耗时 | worker OOM/超时 | 独立 JVM、1GB 默认、文件数/大小上限、include/exclude |
| 方法体局部变量重命名 | 少量误报 | 文档注明；V0.2 规范化局部标识符 |
| SQLite 并发写 | 锁冲突 | 单写者 + WAL + busy_timeout；分析并发 1 |
| 本地无鉴权 | 同机其他用户访问 | 仅绑定 localhost；Docker 只发布 127.0.0.1；文档警示 |
| 许可合规 | 发行受阻 | Spoon 按 MIT；JGit EDL/EPL；NOTICE；依赖扫描 |
| 内部仓库数据泄漏 | 开源风险 | 夹具全自造；校准只存聚合指标；日志无源码 |

## 18. 附录：探针方法与可复现性

探针为临时工程，位于 `/tmp/spoon-probe`，不属于产品仓库；只读解析校准仓库的四个 `src/main/java` 根。

配置：

```java
setNoClasspath(true);
setComplianceLevel(21);
setIgnoreSyntaxErrors(true);
setCommentEnabled(false);
setLevel("ERROR");
```

统计口径：

- Controller：带 `@RestController`/`@Controller` 简单名的类型；
- 映射方法：`getAllMethods()` 中带 Mapping 注解的方法（含继承）；
- 唯一 API：`verb + 组合路径` 去重；
- 项目内调用：接收者类型或声明类型属于模型类型的 `CtInvocation`；
- 未解析访问器：未解析且方法名以 get/set/is/builder 开头的项目内调用；
- 真实未解析调用：未解析且不属于上述命名模式的项目内调用；
- Lombok 访问器存在性：`@Data` 字段对应 `getX` 在 AST 中是否存在。

已执行三轮：

1. FQN 匹配：144 Controller、565 映射方法；发现通配符 import 缺陷。
2. 简单名匹配 + 解析诊断：156 Controller、679 映射方法、689 API；确认 Lombok 与接口/Feign 分布。
3. compliance 21 + 1GB 堆：同上结果，解析 4.23s、已用堆 274MB，确认部署参数可行。

V0.1 实施时，探针逻辑迁入 `moheng-analyzer-java` 的集成测试与校准脚本；探针本身不进入发行物。
